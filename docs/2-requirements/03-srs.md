# 03 · Software Requirements Specification (SRS-lite)

Status: Draft for approval · Priority: **M** Must, **S** Should, **C** Could (stretch).

| Capability | Admin | Technician | Manager |
|---|:-:|:-:|:-:|
| Create / edit order (until In Progress) | ✓ | | |
| Assign / reassign technician | ✓ | | |
| Reschedule (with reason) | ✓ | | |
| Start job, complete job | override* | own jobs | |
| Raise manual flag | ✓ | | ✓ |
| Resolve flag (with note) | ✓ | | ✓ |
| Review (approve / send back), close | | | ✓ |
| View all orders incl. Closed | ✓ | own only | ✓ |
| KPI dashboard, calendar | ✓ | | ✓ |
| Deactivate technician | | | ✓ |

*Admin override requires a reason and is audit-logged.

## 2. Functional requirements

### 2.1 Authentication
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-AUTH-1 | M | Users sign in with email + password (Supabase Auth). | Wrong password shows an error; correct credentials land on the role's home. |
| FR-AUTH-2 | M | Login page offers one-click demo sign-in for each seeded user. | Clicking "Ali" signs in as technician Ali. |
| FR-AUTH-3 | M | Deactivated users cannot sign in. | Sign-in for a deactivated user is refused with a clear message. |

### 2.2 Orders (Module 1)
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-ORD-1 | M | Admin creates an order: customer name, phone, address, problem description, service type, quoted price, scheduled date/time, technician (optional), admin notes. | Required fields validated client and server side; saved order visible in list. |
| FR-ORD-2 | M | Order number is generated by the database as `ORD-YYMMDD-####` (MYT date, daily sequence). | Two concurrent creates never collide. |
| FR-ORD-3 | M | Phone validated as Malaysian and stored as `60XXXXXXXXX`. | `012-345 6789` stored as `60123456789`; invalid rejected. |
| FR-ORD-4 | M | Status = Assigned if technician chosen, else New. | |
| FR-ORD-5 | M | Post-submit summary shows the created order. | |
| FR-ORD-6 | S | Technician picker shows each technician's job count that day and warns of clashes within ±2 h. | Warning shown, assignment still allowed. |
| FR-ORD-7 | S | Admin summary offers "Notify technician on WhatsApp" deep link. | Opens `wa.me` with prefilled job details. |
| FR-ORD-8 | M | Admin may edit order fields while New/Assigned; afterwards only via override with reason. | Edit after In Progress without override is rejected by the server. |
| FR-ORD-9 | M | Admin may reassign while New/Assigned (reason required once assigned); while In Progress only as an override with a reason. | Reason stored in audit log; previous technician loses access. |
| FR-ORD-10 | M | Admin may reschedule (`scheduled_at`), reason required; counted against the assigned technician. | KPI reschedule count increments. |
| FR-ORD-11 | M | Order list: search (order no, name, phone), filters (status, technician, date range, has open flags), 25 per page, includes Closed. | |
| FR-ORD-12 | M | Order detail shows fields, attachments, payment, flags, audit timeline. | |
| FR-ORD-13 | S | Service types come from a lookup table. | |

### 2.3 Technician jobs (Module 2)
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-TEC-1 | M | Technician sees Today / Upcoming / History of own jobs only. | Another technician's job is not retrievable (RLS). |
| FR-TEC-2 | M | "Start job" moves Assigned → In Progress. | Only the assigned technician (or admin override). |
| FR-TEC-3 | M | Completion form: order ID (read-only), work done, extra charges (≥ 0), final amount (auto = quoted + extras), remarks, up to 6 attachments, technician name and timestamp (server-set, not editable). | Tampered technician/timestamp values are ignored by the server. |
| FR-TEC-4 | M | Attachments: image/video/PDF, ≤ 6; image/PDF ≤ 10 MB, video ≤ 50 MB; photos compressed in browser; private bucket, signed URLs. | 7th file and oversize files rejected with a clear message. |
| FR-TEC-5 | S | Payment received: amount, method (Cash/Transfer/Card/QR), optional receipt photo. | |
| FR-TEC-6 | M | "Mark job done" moves In Progress → Job Done. | Only after all uploads complete. |

### 2.4 Review and closing
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-REV-1 | M | Manager review queue lists Job Done orders, flagged first (High → Low), then oldest. | |
| FR-REV-2 | M | Approve → Reviewed. Send back → In Progress with required reason. | |
| FR-REV-3 | M | Manager closes a Reviewed order when payment is settled → Closed. | |
| FR-REV-4 | C | AI may *propose* bulk "mark Reviewed"; applied only after the manager clicks Confirm in the UI. Limits: manager only, Job Done only, unflagged only, ≤ 20 per batch, logged "via AI". | Typing "yes" in chat does nothing. |

### 2.5 Flags
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-FLG-1 | M | On Job Done, the system evaluates rules (thresholds in config): **High** — final > quote by > 20%; extras > 0 with no remarks; payment recorded < final. **Medium** — no attachments. **Low** — final ≠ quote within 20% and remarks given; completed > 24 h after scheduled time. | Each rule has unit tests at and around its threshold. |
| FR-FLG-2 | M | Admin/Manager can raise a manual flag with a level and note. | |
| FR-FLG-3 | M | Flags are Open until resolved with a note; resolver and time recorded. Resolved shows green ✓. | |
| FR-FLG-4 | M | Flags visible to all roles that can see the order; lists sort High → Medium → Low. | |

### 2.6 Notifications (Module 3)
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-NOT-1 | M | When status becomes Job Done, a **database trigger** creates the customer WhatsApp feedback message and deep link. | Works even if status is changed outside the UI. |
| FR-NOT-2 | M | Technician success screen shows "Send feedback request on WhatsApp"; admins can resend; send time logged. | Link opens `wa.me/60…?text=` with the brief's template. |
| FR-NOT-3 | M | In-app bell for Admin/Manager, live via Realtime. High flags notify individually; other completions grouped ("12 jobs completed today"). | |
| FR-NOT-4 | S | Sounds on by default, per-user off switch: job-done confirmation (technician), High-flag chime (admin/manager). | |

|---|---|---|---|

| FR-AUD-2 | M | Audit log page with filters (Admin/Manager). | |

### 2.9 AI assistant
| ID | P | Requirement | Acceptance criteria |
|---|---|---|---|
| FR-AI-1 | M | Floating round AI button bottom-right on every screen opens a chat panel, all roles. | |
| FR-AI-2 | M | Answers come only from whitelisted, read-only, parameterised tools executed under the user's session (RLS). | No free-form SQL path exists. |
| FR-AI-3 | M | Role tool sets: technician (own jobs/stats), admin (jobs, assignment, workload, flags), manager (all incl. KPIs, revenue). Tools outside the role are hidden and rejected server-side. | |
| FR-AI-4 | M | Guardrail pipeline (fail closed at each stage): input screen → intent judge (strict JSON) → main model (≤ 3 tool calls) → structured-only tool results → output screen → blocked log. | All attack cases in the test plan blocked. |
| FR-AI-5 | M | Each answer shows "based on: tool, period". | |
| FR-AI-6 | M | Rate limit 20 questions / user / hour; ≤ 3 turns of history. | |
| FR-AI-7 | M | Supported questions include: jobs by technician and period; top technician; jobs completed today; flags; workload / "who might be overloaded" (SQL computes, AI explains). | |
| FR-AI-8 | M | Blocked request log (user, role, stage, reason, input, time), manager-only. | |
| FR-AI-9 | M | If the AI provider fails, reply "Assistant unavailable" — no fallback provider, no partial data. | |
| FR-AI-10 | M | AI may return customer name, phone and address only to Admin, Manager, or the technician currently assigned to that order. Free-text fields (problem description, remarks, notes, work done) are never returned. | Technician asking for another technician's customer phone gets "I don't have that data"; after reassignment the old technician loses access. |

## 3. Non-functional requirements
| ID | Requirement |
|---|---|
| NFR-1 Responsive | Technician screens mobile-first (375px), touch targets ≥ 44px, primary action pinned bottom. Admin/Manager desktop-first, usable on tablet/phone. |
| NFR-2 Performance | LCP < 2.5 s on 4G for technician home; app-page JS < 300 KB gz. |
| NFR-3 Security | RLS default-deny on every table; service-role key server-only; no secrets in repo; CSP and security headers; server-side validation of every input. |
| NFR-4 Traceability | Every state change has actor, timestamp and (where required) reason. |
| NFR-5 Data correctness | Money as integer sen; all date bucketing in `Asia/Kuala_Lumpur`. |
| NFR-6 Accessibility | WCAG 2.2 AA contrast, keyboard navigation, focus states, `prefers-reduced-motion` honoured. |
| NFR-7 Reliability | AI and notifications fail closed and visibly; uploads retry per file. |
| NFR-8 Maintainability | TypeScript strict; lint/typecheck/tests in CI; files < 800 lines. |
| NFR-9 Licensing | Only assets whose licence permits the use; ITF fonts via CDN; `CREDITS.md`. |
| NFR-10 Locale | English UI, RM currency, `dd/mm/yyyy` dates. |

## 4. Out of scope
Multi-branch, leave/unavailability, Cancelled status, customers table, discounts, monthly reports, drag-to-reschedule, paid WhatsApp API, dark mode.
